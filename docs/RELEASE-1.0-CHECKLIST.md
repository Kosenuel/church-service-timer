# Ready for 1.0.0: checklist

A draft for the owner to edit. It defines what "ready for general use" means before the version moves to 1.0.0. From 1.0.0 on, an incompatible change always means a new MAJOR version (see [Versioning](BUILD.md#versioning)), so the point is to be sure now which things the app promises to keep working.

Tick a box only when it has been checked on the real thing. Items marked **Repo** are already shown by what is in this repository (tests, documents or workflows); that does not replace a check on a real device where one is listed. Items marked **Open** have no proof in the repository yet. Use [test releases](BUILD.md#test-releases-pre-releases) (`1.0.0-rc.1`) to try the build on your own devices first.

## 1. Real-device testing

**Windows PC**

- [ ] Every step of "What to try on a real PC" in [WINDOWS.md](WINDOWS.md#what-to-try-on-a-real-pc) passed on real Windows hardware. **Open:** WINDOWS.md says the app has not been run on a real PC by anyone.
  - [ ] Second screen (step 11), including a screen with a different scale setting, unplugging it and the "open when a service starts" setting.
  - [ ] Full screen (step 15) and the mini timer (step 13), on one monitor and on two.
  - [ ] Notification-area countdown icon (step 14).
  - [ ] Sleep, hibernate and restart during a service (steps 2 and 3).
  - [ ] Download and install proven from an older version (step 16), using a real (not pre-release) newer version on the guide site.
  - [ ] Installer: fresh install, install over an older version, uninstall, and the app's "Open with" entry.
- [ ] A 1366 × 768 laptop and a 1920 × 1080 screen both look right (**Repo:** the window sizes are checked in tests; a real screen is not).

**Android phone and tablet**

- [ ] A phone test pass: start, pause and finish a service; full screen gestures and the notification tray; turning the phone round during a service; locked-screen operation. **Open.**
- [ ] A tablet test pass: the wide layout, orientation, and pairing as host and as second operator. **Open.**
- [ ] Pairing between two Android devices and between a phone and a PC, using the six-digit code. **Open** (the pairing protocol is covered by tests, [W2 evidence](w2-protocol-evidence.json) for the sign).
- [ ] LED sign, if you use one: connect, show a segment, a cue and the end screen on the real sign. **Repo:** the sign codec matches the Java codec used with real signs; **Open** for a sign on the current version.
- [ ] The Android app installs over the previous release, using the same release key and the next build number. **Repo:** the release workflow refuses to publish without the release key.

## 2. Data and compatibility

- [ ] You are willing to keep these stable from 1.0.0 (a change that an older version cannot open needs a MAJOR version): program files (JSON and CSV), backups, the saved state on a device, and the pairing and web-screen protocol. **Decided:** see Decisions 1.
- [ ] The format versions are written down. **Repo, partly:** [TEMPLATE-FORMAT.md](TEMPLATE-FORMAT.md) lists the program file versions and which app version reads each; backups carry a `schemaVersion` (`lib/domain/app_settings.dart`). **Open:** the pairing and web screen versions, and the saved-state version, in one list.
- [ ] An upgrade test from an earlier 0.x with real saved data: install the oldest build still in use, save programs, reports, cues and a backup, update to the candidate, and check everything opens. **Open.** **Repo:** WINDOWS.md says a backup made on either platform restores on the other, and the import code keeps older `schemaVersion`s readable; nothing here replaces a test with real data.
- [ ] Nothing in the app is refused by an older device without saying why. **Repo:** program and backup files that need a newer version say "needs this version or later" and the CHANGELOG names such changes. **Open:** pairing with a phone on an older version shows a clear message rather than failing silently.
- [ ] The rule is applied: reading the CHANGELOG since 0.35.0 shows no entry that needed a MAJOR version.

## 3. Distribution

- [ ] Windows installer: either signed with a code-signing certificate, or a deliberate decision not to sign, with the SmartScreen warning ("Windows protected your PC", then **More info** and **Run anyway**) explained where people download. **Repo:** the release notes and WINDOWS.md already explain the warning; **Decided:** not signing for 1.0.0, deferred by the owner and non-blocking (see Decisions 3); **Open:** the explanation next to the download button on the guide site.
- [ ] Google Play: published, or deliberately left out. **Repo:** [PLAY-RELEASE.md](PLAY-RELEASE.md) is a step-by-step checklist and the release workflow builds the signed bundle; **Decided:** not part of 1.0.0 (see Decisions 4).
- [ ] The guide site is current: download button, install steps for Android and Windows, and the privacy policy page. **Repo:** the release workflow copies each release to the guide site; **Open:** the site's own text.
- [ ] The privacy policy matches what the app does today (Check for updates, the optional automatic check, diagnostics by email). **Repo:** README and Settings › About › Your data describe it; **Open:** the policy page.
- [ ] The release notes for 1.0.0 are written for people, not only for the changelog. **Repo:** the workflow publishes each version's CHANGELOG section.
- [ ] A test release (`1.0.0-rc.1`) has been published, installed from the guide on a phone and a PC, and the real `1.0.0` came as an update from it. **Open.**

## 4. Quality

- [ ] The full test suite passes on GitHub Actions on `main`, and the release workflow's analysis and tests pass on the tag. **Repo:** both run on every release; tick it for the actual 1.0.0 commit.
- [ ] No known crash is open: the issue list has no open crash or data-loss report. **Open.**
- [ ] Accessibility pass on a phone and a PC: large text (system font size at its largest), **High contrast**, **Reduced motion**, and TalkBack or Narrator reading the main controls. **Repo:** High contrast and Reduced motion are settings (Settings › Appearance); **Open:** nobody has recorded a pass with them.
- [ ] A long-service check: a full service of 90 minutes or more runs without the display drifting or the app slowing. **Repo:** [PERFORMANCE-REVIEW.md](PERFORMANCE-REVIEW.md) and the soak script describe the method; **Open:** a recent result.

## 5. Support

- [ ] People can say how to report a problem. **Repo:** Settings › Feedback Center prepares an email; **Open:** the guide says where to send it and what to include.
- [ ] Diagnostics (Settings › Diagnostics) are understood by whoever answers: what they include, and that they contain no church content. **Repo:** the README says so.
- [ ] Someone is named to answer reports, and how quickly. **Open.**

## Decisions

These were open questions in the draft. Each is now decided; the owner can overrule any of them. A follow-up is a task the decision creates; none is done yet unless it says so.

1. **Which things are promised stable?** **Decision:** all four are promised, with the promise worded as "a newer version always opens what an older one saved or shared". Program files (JSON and CSV), backups and the saved state on a device stay readable by every later version, and pairing and web screens keep the timer, countdown, segment names, cues and messages working between any 1.x versions. A new optional feature may still need a newer version to open a file that uses it ("needs this version or later to open"), and that is a MINOR release, as long as a file that does not use the feature still opens in the older version and the older version says why when it refuses one. The LED sign's own protocol is fixed by the sign, so it is not ours to change; the promise is that the app keeps sending what the sign accepts, not that every sign model works. Not promised, and free to change in a MINOR release: how stage screens look, the web screen's page text and layout, the Windows second screen's private channel to the main window, diagnostics, printed reports and the update check's wording. *Reasoning:* the readers already accept every saved-state version (1–16), backup version (1–11) and program version (1–5), so the promise costs nothing new. But the draft's strict rule (a file an older version cannot open is MAJOR) would already have made 0.35.0 a MAJOR release, and would turn every optional cue or screen feature into one, which a volunteer-run app cannot afford. *Follow-ups:* (a) amend [Versioning](BUILD.md#versioning) to say this exactly; (b) write the "what stays stable in 1.x" list in the guide, saying what is not promised; (c) the last item in section 2 (no entry since 0.35.0 needed a MAJOR) is judged by the amended rule.
2. **How far back must an upgrade work?** **Decision:** from every 0.x release, back to 0.1.0. *Reasoning:* all 41 releases are from the last five weeks (16 October to 22 November 2026), so nobody can have a very old install, and the code already reads every older format, so a cut-off would save nothing and only risk saved data. *Follow-ups:* (a) add test fixtures, one saved-state, one backup and one program file for each old version (`test/fixtures` has none), so the promise is tested and not only claimed; (b) the real-data upgrade test in section 2 starts from the oldest build still in use by any church (0.30 if none is known), not from 0.1.0; (c) if the fixtures ever become a burden, raise the cut-off only in a MAJOR version, with a notice in the app.
3. **Windows signing.** **Decision:** deferred by the owner. Not a condition of 1.0.0, and it stays an **Open** item that does not block the release. The unsigned installer goes out with the SmartScreen explanation ("Windows protected your PC", then **More info** and **Run anyway**), which the release notes and WINDOWS.md already give. No certificate is bought now and nobody holds one. *Follow-ups:* (a) the guide's download page says the same thing next to the Windows button (owner, guide repo); (b) revisit when there are enough Windows users, or a free route to signing (for example for open-source projects) turns up; the decision about who holds the certificate belongs to that time.
4. **Google Play.** **Decision:** not a condition of 1.0.0. 1.0.0 means the GitHub and guide downloads. *Reasoning:* a new personal account must first run a closed test with at least 12 testers for 14 days in a row and then wait for Google's review ([PLAY-RELEASE.md](PLAY-RELEASE.md), section 6), which the project cannot schedule, and the app is signed with the same release key either way, so people who install now can take updates from Play later. Play is a normal 1.x release when it is ready. *Follow-ups:* the guide must not say the app is "on Google Play" until it is; the status of the Play listing in section 3 becomes "deliberately left out for 1.0.0".
5. **Real hardware.** **Decision:** the minimum is one Windows PC with a second screen or projector and one 1366 × 768 or 1920 × 1080 laptop screen (the second can be the same PC), one Android phone and one tablet with one of them on the oldest Android in use (7.0 is the lowest the app installs on), the phone and PC paired both ways, and the LED sign the owner's church actually uses, if it uses one. Without a sign test the 1.0.0 notes say the sign has been checked against recorded protocol data only. Other models are welcome but not required. *Tester:* the owner, with one other volunteer who runs real services, on a real Sunday and not only at a desk. *Follow-ups:* the owner writes down which devices these are, and each result goes into the section 1 boxes with the date and version.
6. **Support promise.** **Decision:** best effort, written as such in the guide. A report gets a first reply within 7 days. Only the newest release is fixed: there is no PATCH for an older version once a newer one exists, because updating is free and the app's Check for updates does it in a minute. The exception is a bug that loses or damages saved data, which is fixed in a PATCH of the newest release as fast as possible, with a message to anyone who reported it. No promise of a date for features. *Follow-ups:* the owner is named as the contact (the email address in the Feedback Center), and names a second person who can answer when they are away; both go in the guide.
7. **Accessibility target.** **Decision:** large text, **High contrast** and **Reduced motion** are required, and so is one TalkBack pass on a phone over the main operator path (start, pause, next segment, add or remove time, send a cue, end service, and Settings). A Narrator pass on Windows is wanted but does not block 1.0.0; if it has not been done, the guide lists it as not yet checked. *Reasoning:* the layouts are already tested at large text, so the first three cost little, and a screen-reader pass shows whether the main controls have usable names; Narrator needs a Windows PC and a person who knows it. *Follow-ups:* write the TalkBack steps as a short list in WINDOWS.md or a new page, and record the result; fix what the pass finds that stops a person starting, pausing or ending a service.
8. **Release candidate.** **Decision:** `1.0.0-rc.1` runs on the owner's own devices for at least 14 days and through at least 2 real services, one of them with a second device paired. A fix to timing, pairing or saving data restarts the 14 days with `rc.2`; any other fix does not. The final `1.0.0` is the same code as the last rc apart from the version number. *Reasoning:* two Sundays is the least that shows a real service; the usual gap between 0.x releases has been days, so 14 days is a clear pause that still ends. *Follow-up:* none, once the rc is cut (see [Test releases](BUILD.md#test-releases-pre-releases)).
9. **Pairing with older versions.** **Decision:** within 1.x, any 1.x phone, tablet or web screen and any 1.y host must always pair and show the timer, countdown, segment names, cues and messages. Newer features may be missing on the older device (as happens now: steady text for a new effect, white and full screen for a new cue colour), but pairing is never refused for being on a different 1.x version, and "needs this version or later" is not acceptable for pairing within a MAJOR version. The draft said the CHANGELOG already has such pairing changes; it has not: the "needs this version or later" entries are about backups and program files, and pairing changes so far degrade on an older screen. The pairing messages carry no version number today, so there is nothing for an older device to show. *Follow-ups:* (a) add an optional app version to the pairing hello, so a later breaking change could show a clear message and so a report says what each device runs; (b) add a test that a current host's snapshot, with the new fields removed, still shows the timer and cues on the current screen, and keep one recorded snapshot from an earlier version as a fixture; (c) the section 2 item about older devices is judged by this rule.
