# Church Service Timer on Windows

Windows is a second platform of the same app, not a separate one. Every screen, the service model, the file formats and the backups are the Dart code Android uses. Only the layer that talks to the device differs: on Android it is Kotlin behind one method channel, on Windows it is Dart in `lib/windows/`, with a few direct Windows calls in `lib/windows/win32_api.dart`.

A backup made on either platform restores on the other. Saved LED sign passwords travel only inside a backup that was exported with passwords and a passphrase, exactly as between two phones.

## What has and has not been run

Be clear about this when reading the rest of the page.

- **Tested here (Linux), on every change:** everything in `lib/windows/` and `lib/hardware/w2/` except the calls in `win32_api.dart`. That covers the clock across sleep and restart, atomic saves, the secrets vault (with a stand-in for Windows' encryption), the LED sign transport against a synthetic sign on real UDP sockets, file import and export rules, church pictures, Tinos rasterizing, warnings, window memory, the single-copy hand-over, the keyboard keys, the wide layout, and the mini timer's sizes, remembered places and screen (against a stand-in for the window).
- **Checked against Android:** the Dart sign codec produces the same bytes as the Java codec the Android app has used with real signs (`test/fixtures/w2_java_vectors.json`, generated by running that Java code).
- **Not yet run by anyone:** the app on a real Windows PC. The Windows runner (`windows/`), `win32_api.dart`, the installer and the packaging script have not been compiled or executed, because this work was done in a Linux container and the repository's GitHub Actions jobs were not starting. The first Windows build may need small fixes.
- **Full screen window calls: not compiled, not run.** `enterFullScreen` and `leaveFullScreen` in `win32_api.dart` were written from the Windows documentation, on top of `fillScreen` and `restoreWindowPlacement`, which the stage window and the window memory already use, and have never been built or run. Everything around them is tested with a stand-in window. Step 15 below is the check.
- **Mini timer window calls: not compiled, not run.** `pinWindow` in `win32_api.dart` (three Windows calls) and the mini timer's smaller minimum size in `windows/runner/win32_window.cpp` were written from the Windows documentation and have never been built or run. Everything around them is tested with a stand-in window, which proves the app asks for the right things in the right order, not that Windows does them. Step 13 below is the check.

## How each part works on Windows

| Part | Android | Windows |
|---|---|---|
| Clock | `elapsedRealtime()` and the boot count | `GetTickCount64`, which keeps counting through sleep and hibernation. Windows has no boot count, so `BootTracker` works out whether Windows has restarted from "now minus the counter" and a small marker file. If in doubt it says "restarted", which only makes the app fall back to the date and time and ask the operator to review, as after a phone restart. |
| Saved service | `AtomicFile` | `AtomicTextFile`: write a temporary file, flush, keep the previous version as `.bak`, rename into place. A damaged file falls back to `.bak`. |
| Where data lives | App-private storage | `%APPDATA%\I-Proton\Church Service Timer` (not removed when the app is uninstalled). |
| Sign and pairing secrets | Android Keystore | Windows DPAPI, bound to the Windows user account on that PC. |
| LED sign | UDP sockets bound to the Wi-Fi network | The same protocol and the same guards in Dart (`lib/hardware/w2/`): firmware V6.02.232 only, 32 × 16 single colour, only the three program shapes the app builds. The search goes out on every network the PC is on, so Ethernet plus the sign's Wi-Fi works. |
| Joining the sign's Wi-Fi | The app asks Android to join | Not done by the app. Windows joins networks itself; the app opens Windows Wi-Fi settings. Saved Wi-Fi details are kept so backups stay complete. |
| Stage screens and web screens | Same Dart code | Same Dart code. The address shared with other devices avoids virtual adapters and the sign's own network when there is another. |
| Finding a host on the network | `nsd` plugin | Same plugin, which supports Windows. |
| Import, export, backup | System document picker | Windows Open and Save dialogs (`file_selector`). "Share" becomes Save: one file gets a Save window, several go into a chosen folder without replacing anything. |
| Opening a program file | "Open with" and Share | A `.json` or `.csv` passed on the command line; the installer adds the app to "Open with". A second copy hands the file to the one already running. One `.json` or `.csv` dropped on the main window is offered the same way: the runner accepts drops (`DragAcceptFiles`, `WM_DROPFILES` in `windows/runner/flutter_window.cpp`) and sends the paths on the `church_service_timer/window` channel (`lib/windows/file_drop.dart`). Other files, folders and several files are refused, as is any drop while a service runs or controls are locked. The stage window does not accept drops. |
| Church logo and banner | Android bitmap code | The same rules in Dart (`desktop_images.dart`). |
| Tinos on the LED display | Android canvas, no antialiasing | Flutter's text engine (`lib/display/tinos_rasterizer.dart`), a pixel lit at 45% coverage. Close to Android but not identical, especially at 7 rows. |
| Printing | `printing` plugin | Same plugin (Windows print dialog). |
| Staying alive | Foreground service, lock-screen card | A desktop app is not suspended. While a service runs or screens are shared, Windows is asked not to sleep or turn the screen off. Closing the window during a service asks first. |
| Operator warnings | Notifications with sound | A Windows notification (a corrected copy of `local_notifier` in `third_party/`) and a flashing taskbar button. No sound unless **Settings › Warnings & alerts › Play the Windows notification sound** is turned on; it is off to begin with, because a PC is often plugged into the sound system. The choice is kept on that computer and is not part of a backup. Windows holds notifications back under Do not disturb, which it turns on when a screen is duplicated; the flash still shows. The first notification adds a Start-menu shortcut if there is none, because Windows requires one. |
| Countdown when another program is in front | Ongoing notification | An icon in the notification area while a service or quick timer runs (`Shell_NotifyIconW` through `dart:ffi`; `lib/windows/tray_countdown.dart` decides when, `win32_api.dart` makes the calls). Its tooltip is the countdown, changed only when the text changes, about once a second. A click brings the window forward: Windows sends the click to the app window as `WM_APP + 0x3C7`, answered by one case in `win32_window.cpp`. It has no menu and cannot change a service. It is removed when the service ends, when the setting **Show the countdown in the notification area** is turned off, and when the window closes; after a crash Windows removes it the first time the mouse passes over it. If Explorer restarts, the icon comes back within about ten seconds while the countdown runs (when paused, at the next change of text); `TaskbarCreated` is not listened for. Windows 11 puts a new icon in the overflow behind the arrow until it is dragged out. |
| Camera QR scanning | `mobile_scanner` | Not available; the button is hidden. Join with the six-digit code. The PC can still show a QR for phones to scan. |
| Battery optimisation | Settings screen | Does not apply; hidden. |
| Check for updates | Opens the download page | Also **Download and install**: the installer is downloaded, checked and started after the operator confirms, then the app closes (`lib/app/update_installer.dart`, `lib/windows/windows_updates.dart`). |
| Feedback email | Email app | The PC's email program through a `mailto:` link. A long message is put on the clipboard with a note to paste it. |

Only one copy of the app runs per Windows user; starting it again brings the first to the front.

## Desktop layouts

In a window at least 1200 wide and 600 tall, Live uses a desktop layout, chosen in **Settings › Desktop layout** (the same page as **Settings › Appearance**, on its second tab, **Layout & accessibility**). This is not Windows-only: a 10-inch or larger Android tablet in landscape gets it too, where the setting is called **Tablet layout**. Phones never have a window that large, so they do not show the setting (`lib/shared/layout_device.dart` decides from the whole screen, not the window: a shorter side under 600 is a phone, and a tablet needs a longer side of at least 1200).

- **Mission control** (the default): a status strip (ahead or behind, time now, planned finish, now ending, End service), then the timer, stage preview and cues side by side, with the rundown as a timeline along the bottom and the Live keys listed under it. It keeps the side rail. The timeline is `RundownTimeline` in `lib/live/mission_control_live.dart`.
- **Three panes**: the rundown on the left, the timer in the middle, the stage preview and cues on the right, with Live, Programs, Reports and Settings as tabs in the header. Each pane scrolls on its own. With no service loaded, Live keeps its single centred column.
- **The dial**: Three panes with the service ring in the middle in place of the countdown dial: the whole service as a ring ending at the cross, the running segment's time left as an inner ring (`ServiceDial` in `lib/live/service_dial.dart`). It arrives with Royal Navy.
- **Keys**: the dense layout. A strip with the running segment, a large countdown and the controls; the rundown as a table (`lib/live/keys_live.dart`); the stage preview and cues beside it; the keys along the bottom. Automatic spacing is Compact, and it arrives with Graphite. Before the first segment starts it shows the three panes.
- **Classic**: the side rail and one column of cards, as before.

A layout arrives with a theme (Mission control with Midnight Lime); any theme can be chosen afterwards. **Save this look** stores the layout, theme, spacing, contrast and key labels under a name; saved looks are included in backups, while the layout in use stays on the device like the other appearance settings. **Reset to default** returns to Three panes with Midnight Lime.

The layouts only arrange the same timer, cues, stage preview and rundown that the phone uses (`lib/live/desktop_live.dart`), so a change to one of those shows everywhere. Smaller windows, and the focused operator view, use the phone and tablet layout.
## Second screen

The stage output, full screen and borderless, on a projector or second monitor plugged into the PC. Windows must be set to Extend; with Duplicate there is only one screen to Windows.

**On Live**, under the stage preview in every layout (and in the command palette, Ctrl+K), one line says what the second screen is doing and one button changes it: "Second screen: not showing" with **Show on second screen**, or "Showing on Screen 2 · 3840 × 2160" with **Stop**. With more than one extra screen, a list beside the button chooses which. With none, the line reads "No second screen connected" and there is no button. Lock controls disables the button like every other control.

**Settings › Screens & devices › Second screen** has the same Show and Stop for each screen, plus:

- **Open the second screen when a service starts** (off to begin with). Starting a service or a Quick timer shows the stage on the screen it was last shown on, if that screen is connected and nothing is showing yet. If it is not connected, nothing opens and the status line says so. It never opens on the main screen by itself, and a practice run does not open it. Ending the service leaves it open for the end screen, or the clock for a program with no end screen; it closes with Stop, Esc on that screen, or closing the app.
- **What the second screen shows**: Timer only, Timer and segment name, or Timer and next segment. This is the second screen's own choice; paired stage screens keep theirs.

These choices, the screen last used (its place on the desktop and its number) and whether it was showing are kept in `settings.json` on that computer (`SecondScreen` in `lib/windows/second_screen.dart`, through `DevicePort.secondScreenSettings`), not in the app's state or backups. A screen is recognised by its place and size, so it is still found if Windows renumbers the screens; after a change of resolution or arrangement, press Show once to choose it again.

Flutter draws one window per running app, so the stage window is a second copy of the app started with `--stage-output` (`lib/windows/stage_output_app.dart`). It does not run a service or touch saved data. The main app (`StageOutputHost` in `lib/windows/stage_output.dart`) sends it the same picture a paired stage screen gets, over a connection bound to this computer only and opened with a one-time token. It is sent whatever the display is set to. If the main app closes, the stage window closes; if the main app stops sending for a few seconds, the stage marks its timer as out of date. Esc on the stage window closes it.

### Programs in a desktop layout

Programs fills the window in three columns (`lib/programs/programs_desktop.dart`): the program list, the chosen program as a table of its segments, and a summary with Load into Live. Editing still goes through the one program editor (Edit program, or a double-click on a row), so validation, drafts and program history keep a single path. While Live, Programs or Reports fills the window the page behind it does not scroll; each column scrolls on its own.

### Reports in a desktop layout

Reports also fills the window (`lib/reports/reports_desktop.dart`): the report list on the left and the chosen report beside it, with a planned-against-actual picture (a twin timeline, or a ring in The dial) above a table of every segment. The picture shares its drawing code with Live's timeline and dial. Printing, export and the saved report format are unchanged, and narrow windows and Classic keep the list-and-detail page.

## Full screen on this screen

For when the operator's own screen is the one people watch: a laptop on a lectern, or a PC plugged into one television. During a service or a quick timer, the **Full screen** button at the top right of Live (beside Lock controls), **Live › ⋮ › Full screen**, **Full screen** in Commands, or **F11** replaces the app with the stage picture on black: the same `StageSurface`, fed the same snapshot, as the second screen (`HomeState.hostStageSnapshot` is `AppController.stageWindowSnapshot`). Warnings, cues, messages, the clock and a blank screen show as they do on a stage screen. Nothing changes in what the second screen or paired screens receive. A device joined to another's service as a stage screen has its own full screen and is not offered this one.

- **What it shows** is the choice made for the second screen in Settings › Screens & devices: Timer only, Timer and segment name, or Timer and next segment. It is kept on that computer. A phone or tablet has no second screen, so it has the same three choices under **Full screen on this phone** in Screens & devices, kept in that device's own state (`AppState.fullScreenLayout`) and left out of backups.
- **Leaving.** Esc, F11 again, or **Exit** in the control tray. A small **Exit full screen** control also shows at the top right for the first four seconds. When the service ends it stays, showing the end screen (or the clock, for a program with no end screen), with Cues, Clock, Blank and Exit still working; it closes when the next service is set up. Android Back leaves it too (with the tray showing, Esc and Back put the tray away first).
- **Gestures.** A double tap or double click asks, in the same compact card as the keys: the left third of the stage, Undo (only when there is a segment change to undo; otherwise a short "Nothing to undo" fades in and out); the middle, Pause or Resume; the right third, Next segment (on the last segment, "This is the last segment").
- **Control tray.** A single tap or click (after the double-tap wait, about 300 ms), a swipe up from the bottom fifth of the screen, or the mouse at the bottom edge brings up a tray along the bottom: Pause or Resume, Next, −2 min, +2 min, Undo, Cues (a list of the saved cues; the one showing goes back), Show clock or Show timer, Blank or Unblank, End service (End timer for a quick timer) and Exit. Timer actions ask first, as on Live; after End service, full screen stays on the end screen, or the clock for a program with no end screen. It goes after six seconds untouched (`HostFullScreenView.trayTime`); a touch or key in it starts the six seconds again, and it stays while the mouse is over it or a question from it is open. Esc, Back or a swipe down hides it. It is drawn over the stage on this screen only and is never part of the stage snapshot. With Reduced motion it does not slide.
- **Keys.** They work as on Live, with the same rules. A timer action asks first in the compact card the mini timer uses, over the stage; Next still needs its second press; Adjust time opens its usual dialog. With **Lock controls** on, every key, gesture and the tray are blocked, Esc and F11 included; a click, or Esc, shows **Controls locked** and **Hold to unlock** in place of Exit.
- **The window.** On Windows the app window loses its title bar and borders and covers the monitor it is on (`WindowMemory.enterFullScreen`, through `DevicePort.fullScreenWindow`), then goes back to exactly where and as large as it was, maximised if it was. While it is full screen its place is not saved, so closing the app then opens the normal window next time. If Windows refuses, the stage still fills the window as it is. It cannot be opened from the mini timer, nor the mini timer from it. On Android the system bars are hidden (immersive) while it shows and put back on leaving.

`HomeState.setHostFullScreen(bool)` opens and closes it (`lib/live/host_full_screen.dart`).

## Mini timer

For a laptop that also runs the lyrics or slides. During a service, **Live › ⋮ › Mini timer** shrinks the app to a small window (about 380 × 150) that stays above other programs. It shows the running segment, the countdown in the same colours as the dial (amber near the end, red and counting up with a "+" in overtime), what is next, how far ahead or behind the service is, and a bar for the time left. Its buttons are Pause or Resume, Next, the first prepared cue (which turns into Show timer while that cue is on the stage) and Expand. Pause, Next and closing the window ask the same questions in the same words as the full window, in a compact form that fits; Adjust time needs the full window and says so. With Lock controls on, the buttons give way to Hold to unlock. Dragged narrower than about 260, the window shows only the name and countdown. The keys work as on Live. Warnings stay silent, as everywhere on a PC.

Expand, or the service ending, puts the window back exactly where and how it was (size, place, maximised or not) and no longer on top. The mini window's own place is remembered separately for next time. If the app is closed while small, it opens as the normal window at its usual place.

How it works: the app asks the port for a `MiniWindow` (`lib/windows/mini_window.dart`: `enter`, `leave`), which only Windows provides; without one the menu entry does not exist. On Windows it is `WindowMemory` (`lib/windows/window_memory.dart`), the same code that remembers the window's place, so the two cannot disagree: while small, `window.json` keeps the normal window under `window` and only the small window's corner under `mini`. A file from an older version has no `mini` and loads as before. Moving and sizing use the calls window memory already used (`GetWindowPlacement`, `SetWindowPlacement`, and `MonitorFromRect` to refuse a place that is on no screen). The one new function, `pinWindow`, reads the window style (`GetWindowLongPtrW`), clears or restores the maximise button's bit (`SetWindowLongPtrW`), and moves the window into or out of the always-on-top band (`SetWindowPos` with `HWND_TOPMOST` or `HWND_NOTOPMOST`, not moving, sizing or activating). The runner normally refuses a window smaller than 420 × 640; it allows 180 × 90 while the window is always on top, so the window is pinned first and sized second. The size asked for is the inside of the window: the title bar and borders are measured from the normal window (its outside size minus the size Flutter draws into), with the usual Windows 10 and 11 frame assumed when that cannot be trusted (maximised or snapped).

Known limits: a window that was snapped to a screen edge comes back at the size it had before it was snapped, because that is what Windows reports. On a screen with a different scale from the one the normal window was on, the small window can come out a little larger or smaller than 380 × 150.

`HomeState.setMiniTimer(bool)` opens and closes it. **Ctrl+M** and the **Mini timer** entry in Commands call it too; Ctrl+M does nothing while the controls are locked or while typing.

## Keyboard on Live

Every key is listed once, in `lib/live/shortcuts.dart`. The shortcuts sheet, the key shown beside each command in Commands, the clicker test page and the table below all follow that list, and `test/live/shortcuts_sheet_test.dart` holds the list to what `HomeState.onClickerKey` really does: a key that is added without being listed, or listed without doing anything, fails the test.

| Keys | What it does | How it confirms |
|---|---|---|
| **Space** or **B** | Pause or resume | Asks first |
| **Page Down** or **→** | Next segment | Press twice to confirm |
| **+** or **−** | Adjust time | You choose, then confirm |
| **Ctrl+Z** | Undo the last segment change | Asks first |
| **J** | Jump to a later segment | You choose, then confirm |
| **R** | Recover time | You choose, then confirm |
| **E** | Edit upcoming | You edit, then save |
| **Ctrl+L** | Lock controls | At once; hold to unlock |
| **1** to **9** | Show a prepared cue | At once; again to go back to the timer |
| **M** | Send message | You type, then send |
| **Ctrl+K** | Commands | A list of everything you can do now |
| **Ctrl+M** | Mini timer | A small window on top; again to leave it |
| **F11** | Full screen | The stage on this screen; again or Esc to leave it |
| **?** or **F1** | Keyboard shortcuts | This list |
| **Enter** or **Space** | Confirm the question on screen | Not End service, which must be clicked |
| **Esc** | Cancel or close | Nothing is changed |

Two rules hold for all of them: every timer action asks to confirm before anything changes, and **Lock controls** blocks every key until it is held to unlock (Ctrl+L locks and cannot unlock).

- **When they work.** The keys from Space down to M work on Live while a service is running, with no question or other page on top; the cue numbers and M also need a display connected. Ctrl+Z needs a segment change to undo and J a later segment to jump to. Ctrl+K and ? or F1 work on any tab of the home screen, but not under a dialog or another page. Ctrl+M works whenever a service is running, whatever page is showing. F11 does too, and in full screen the keys from Space down to M work as they do on Live. None of them does anything while typing in a field, so ? typed into a field is a question mark.
- **Clicker keys.** Space, B, Page Down and → are the keys a clicker or pedal sends. They work only while **Clicker and foot pedal** is on (it is on to begin with), on a computer as well as a phone or tablet: a computer cannot tell a clicker from its keyboard, so switching it off turns them off on the keyboard too, and the buttons, key labels and shortcuts sheet stop offering them. The other keys in the table do not depend on it. Holding Ctrl makes no difference to them. On a phone or tablet they need that setting, and a clicker's Space or B pauses at once, because there is no screen in the hand to confirm on; the other keys in the table need a computer.
- **Other spellings.** The + key works without Shift (the = key), the number pad's + and − open Adjust time, and its 1 to 9 send cues. The number of the cue that is showing goes back to the timer.
- **In a question.** Space or Enter presses the confirming button and Esc cancels, except for End service and the other destructive questions, which must be clicked.
- **Key labels.** On a computer the buttons show their key; **Show keyboard keys on buttons** in Settings › Appearance turns that on or off.

### Shortcuts sheet

**?** (Shift and /) or **F1** opens the list above as a dialog (`lib/live/shortcuts_sheet.dart`); so do **Keyboard shortcuts** in Commands, in the Live ⋮ menu and in Settings search. Esc closes it. It does not open while the controls are locked, in the mini timer, or under another dialog.

### Testing a clicker or pedal

**Settings › Warnings & alerts › Test a clicker or pedal** (`lib/settings/clicker_test_page.dart`) names each key as it is pressed ("Page Down", "Right arrow", "F5") and says what it does on Live, or that the app does not use it, and keeps the last few presses. While the page is open nothing pressed reaches the service: `onClickerKey` returns at once, so there is no timer action, no question and no mini timer. Tab, Enter and Esc still do their ordinary job there, so the page can be left from the keyboard. It works on Android too, where a Bluetooth clicker sends keys.

## Commands

**Ctrl+K**, or **Commands** in the Live ⋮ menu, opens a searchable list of what can be done now (`lib/live/command_palette.dart`). It works on any tab of the home screen, but not under a dialog, while typing in a field or with the controls locked. Each command calls the same function as its button, so timer changes still ask to confirm, and a command is listed only while its button would be enabled.

## Updating from the app

Settings › About › **Check for updates** asks GitHub's public API for the latest release of the guide repository when pressed. When it is newer, a PC offers **Download and install** beside **Open release page**; a phone offers only the page, as before.

- **Automatically.** Under it, **Check for updates automatically** (off to begin with) makes the same request by itself, at most once every 24 hours: 30 seconds after the app starts, and again when the app comes back to standing by (`lib/app/auto_update_check.dart`). With it switched on, the app contacts GitHub once a day; with it off, only when Check for updates is pressed. It never asks while a service, quick timer, rehearsal, guided practice or Check this service is running, while the controls are locked, or while this PC is joined to another device's service. A newer version shows a small notice on Live while standing by, **Version X is available**, with **See update** (opens Check for updates, after the Settings PIN if one is set) and **Not now** (hides it for that version; a newer one shows it again). Nothing is downloaded or installed until **Download and install** is pressed and confirmed, as above. The notice is never on a stage screen, the second screen or full screen. A failed check says nothing and waits a day. The switch, the time of the last check and the version found are kept in the app's saved state on this PC (`autoUpdate`), not in backups or program files.

- **Which file.** Only `Church-Service-Timer-<version>-windows-setup.exe` from that release, with exactly the version offered, downloaded from the guide repository's releases. A release with only the zip, or no Windows file, gets **Open release page** and a line saying why: a zip cannot be installed by the app.
- **Checks.** The download goes to a new folder in the Windows temporary folder with a progress bar and **Cancel download**. It must be exactly the size GitHub lists. When the release has `<installer>.sha256` (written by `scripts/Package-Windows.ps1`) or GitHub lists a SHA-256 for the file, the download must match it, and the two must agree. A file that fails is deleted. With no checksum at all only the size is checked, and the question says so.
- **Asking.** Nothing is installed without a question: "The app will close to install version X…". A running service blocks it ("Finish or end the service first"), checked before downloading and again after the question, as does a service report still being saved. Drafts being edited are saved first; they are kept in the saved state and offered again when the app reopens.
- **Installing.** The installer is started as it would be by a double-click, with no arguments, so it shows every step; then the app closes as if its window had been closed. If Windows will not start it, the app stays open and says where the file is.
- **Where it comes from.** `publish-to-guide.yml` copies the Windows installer and its `.sha256` to the guide release along with the APK, after the Windows build has finished. A release made before this change has no installer there, so a check against it falls back to the release page; run **Actions › Publish to the guide site** with that tag to add it.

## Building

On a Windows PC with Flutter 3.47.7 and Visual Studio 2022 ("Desktop development with C++"):

```
flutter pub get
flutter build windows --release
pwsh scripts/Package-Windows.ps1
```

The app is in `build\windows\x64\runner\Release`; the script writes a zip and, with [Inno Setup 6](https://jrsoftware.org/isinfo.php) installed, an installer to `dist\`. `build.yml` does the same on GitHub and uploads the result as the `church-service-timer-windows` artifact; `release.yml` attaches both files to a tagged release.

Nothing is code-signed. Windows SmartScreen shows "Windows protected your PC" the first time; **More info** then **Run anyway** starts it.

## What to try on a real PC

1. **It starts.** Unzip, run `church_service_timer.exe`. The window is titled Church Service Timer with the ring-and-cross icon, and opens on Live.
2. **Sleep during a service.** Start a service, note the time left, close the lid or choose Sleep for two minutes, wake the PC. The timer should be two minutes further on, with no "review" prompt. Repeat with Hibernate.
3. **Restart during a service.** Restart Windows mid-service and reopen the app. It should carry on from the clock and ask you to review, not show the old time.
4. **Close and reopen.** Close the window during a service (it should ask first), reopen: the service continues. Move and resize the window, close, reopen: same place and size.
5. **Web screens.** Turn on sharing. Windows Defender Firewall should ask once; allow it on private networks. Open the address shown from a phone on the same network.
6. **Pairing.** Pair a phone with the PC as host, then join a phone's service from the PC with the six-digit code.
7. **LED sign.** Join the sign's Wi-Fi in Windows, then scan and connect in the app. Try it with Ethernet also plugged in.
8. **Files.** Import a program, export one, make a backup and restore it; restore a backup made on the phone.
9. **Second copy.** Start the app twice: the first window should come forward. Right-click a `.json` program, Open with, Church Service Timer. Then drag a `.json` program from a folder onto the window: the import review should open. Drop a picture, a folder and two files together: each should be refused in one line. Drop a program during a service and with controls locked: nothing is imported. Drop one on the mini timer, and on the second-screen window, which should not accept it.
10. **Fonts.** Make a cue in Tinos at 7 and 14 rows and compare it with the phone.
11. **Second screen.** Plug in a projector or monitor, press Windows + P and choose Extend. On Live, the line under the stage preview should read "Second screen: not showing"; press **Show on second screen**. It should fill that screen with the timer, with no title bar or taskbar, and follow pause, cues, messages and Blank screen, and Live should read "Showing on Screen 2" with that screen's size.
