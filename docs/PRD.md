# PRODUCT REQUIREMENT DOCUMENT (PRD)
## Church Service Timer & Alert Controller (LedArt-Lite Alternative)

## 1. Context & Goal
The objective is to build a dedicated church production timer and alert application designed to replace generic, rigid LED matrix utilities like LedArt-Lite. Version 1 will run on Android phones and tablets in the church tech booth. It will connect directly to a 32x16 pixel LED matrix sign over its local Wi-Fi Access Point (Huidu architecture) to act as a smart stage production timer and discreet communication system for pastors, speakers, and worship leaders.

The physical display hardware remains a fixed, pre-existing commercial 32x16 LED matrix driven by a Huidu Wi-Fi control card (e.g., HD-WF1 or HD-WF2). **Do not write firmware for microcontrollers.** Write a high-level application that interfaces with the card's verified local Wi-Fi address (candidate examples: `192.168.4.1` or `10.10.10.1`) and pushes raw network data (TCP/UDP socket packets or HTTP POST configurations) to update and render text or countdown clocks onto the 32x16 grid.

---

## 2. Technology Stack & Platforms
- **First Supported Platform:** Android phones and tablets. Desktop and iOS are outside version 1.
- **Framework:** React Native with TypeScript or Flutter with Dart, selected after the protocol feasibility investigation. Native integration must support the verified transport and required Android lifecycle behavior.
- **Connectivity:** Manual connection to the controller Wi-Fi is the baseline. Automatic switching is optional and must be verified on supported Android versions. Live operation and saved templates must work without Internet access.
- **Android Lifecycle:** Establish the supported Android versions and device test matrix during implementation. Specify and test the execution mechanism needed for screen lock/background operation; a correct clock alone does not ensure continued network output while the application is suspended or terminated.

---

## 3. System Architecture & Pages
Separate Live Production Mode from Template Management and Display Settings. The active service uses an independent snapshot of its timeline, cue definitions, and display settings. Template edits affect future services and must not mutate the current run. Device connection settings are separate, local-only settings and are not part of a template or service snapshot. Replacing the active timeline requires explicitly ending the current service and starting another.

Provide high-contrast controls optimized for Android touch interaction. No structural timeline editing is permitted here.

#### 3.1 Start and End Service
- **Start Service:** Open a popup offering Select Saved Timeline or Create Timeline. Creating a timeline opens the setup editor and returns to the start flow when saved. Show the selected sequence, load an independent snapshot into the active service screen, and require an explicit Start First Segment action to begin timing. Cancelling the popup does not change the sign or start a timer. A timeline must contain at least one valid segment.
- **Ready State:** After loading a timeline and before Start First Segment, show Ready with the first segment and its configured duration. No countdown runs and no automatic display command is sent; retain the sign's previous output. Disable Pause/Resume, Add, fixed adjustments, Advance, Undo, and cue sending until starting. Allow Start First Segment or Cancel Setup; cancellation returns to the prior idle/ended view without sending anything or reviving cancelled output retries. Persist Ready so reopening never starts the timer automatically. Disable Start Service while Ready. Start First Segment commits once and begins timing even if disconnected, with a prominent delivery-status warning. End Service is enabled only after the service has started.
- **End Service:** Ask for confirmation, stop the active timer, clear any active alert, mark the service ended, and request the configured end display. The default text is **Hallelujah**. Display Settings allows the user to replace it with formatted custom text. Persist the ended state so reopening cannot revive an ended service.
- **Final Segment:** Do not advance or end automatically. Disable Advance when there is no next segment. At zero, retain the configured zero-time screen until the operator explicitly ends the service or adjusts the time.

#### 3.2 Countdown and Zero-Time Behavior
- **Elapsed-Time Countdown:** Calculate remaining time using an authoritative monotonic elapsed-time model during the current device boot/session. Never subtract one second per scheduled callback. UI refreshes and network activity must not determine elapsed time. Device wall-clock changes must not alter an ongoing countdown when its monotonic reference remains valid.
- **Display Updates:** Target one update per second while displaying a running countdown, using the current calculated value. Discard missed intermediate values after scheduling delays. Verify transport cadence and readable time formatting against the physical 32x16 display.
- **Pause:** A dedicated control freezes remaining time and changes its label to Resume while paused. Resume continues from the frozen value. This control is separate from Add and the fixed adjustment buttons. Showing or dismissing an alert does not change this state.
- **Separate Adjustment Controls:** Provide **Add**, **-2 minutes**, and **+2 minutes** as distinct buttons beside Pause. Add opens a custom-duration popup with minutes and seconds fields, Cancel, and Add Time; require a positive total duration and seconds from 0 to 59. The fixed buttons subtract or add exactly 120 seconds per intentional tap. Apply adjustments to authoritative state immediately, including while paused, without dismissing an active alert. Clamp remaining time to zero; never display negative time. Adding time after expiry returns the segment to a running countdown unless explicitly paused. Cancelling Add changes nothing; confirming it must commit only once.
- **At Zero:** Stop at zero without overtime or automatic advancement. Display Settings offers (1) **Show 00:00**, the default, or (2) **Custom Zero-Time Screen**, configured using the formatted text/layout editor. The Custom Zero-Time Screen supports formatted text only in version 1, with supported positioning and text effects. Image, video, and image-background content are outside scope. An active alert remains above either zero-time screen until dismissed.

#### 3.3 Advance Confirmation and Undo
- Tapping **Advance** opens one confirmation popup showing the next segment name and duration, with Cancel and **Start Next Segment** actions. The current timer continues normally while the popup is open. If an alert is active, explicitly state that it will remain visible while the next timer runs underneath it.
- Confirming commits exactly one transition, starts the next segment running at its configured duration even when the previous segment was paused, and persists that transition. Label the confirmation action with the next segment and duration (for example, Start Closing — 5 minutes). The previous pause state is retained only in the undo checkpoint. Disable confirmation while committing, ignore duplicate touch events for that transition, and require a fresh confirmation for another advance. Network retries must never advance the timeline again.
- **Undo Advance:** Retain a one-step checkpoint of the previous segment, remaining time, pause state, and transition timestamp. Make undo available until another advance or End Service; show the segment it will restore. Undo restores the previous timer as if the accidental advance had not occurred: deduct elapsed time since the transition if it was running, keep its value if paused, and clamp at zero. For example, undoing after 5 seconds restores 2:55 from a previously running 3:00 timer, or 3:00 if it was paused. Changes made to the accidentally selected segment are discarded. Undo preserves the currently active alert and is itself protected against duplicate taps. Permit one-tap undo only within 10 seconds of advancing and only if no time adjustment or pause/resume action has occurred on the new segment. Otherwise show a confirmation naming the segment to restore, its projected remaining time and pause state, and the current segment changes that will be discarded. Recalculate at confirmation time. Cancel changes nothing. Persist the transition time and modification flag across reopening; require confirmation if elapsed time is uncertain. Successful undo consumes the checkpoint so it cannot be repeated.

#### 3.4 Stage Cues and Custom Text
- Maintain 4 to 6 configurable quick cues such as WRAP UP, TIME'S UP, MIC LOW, and NURSERY CALL. The latest alert replaces the previous alert; do not queue old alerts for later playback.
- Treat ALERT and TIMER as internal application priorities. Alerts supersede countdown and zero-time output. Advance changes the underlying segment but leaves the alert visible. End Service explicitly clears the alert and requests the end screen.
- Continue calculating an unpaused timer beneath an alert. **Show Timer** dismisses the alert and shows the current countdown or configured zero-time screen; it does not resume an explicitly paused timer.
- Custom text supports formatting, including **bold and italic**, with the text/style operations in LedArt-Lite 2.3.14 serving as the investigation reference. Investigate font choice/size, alignment, color, scrolling, and flashing; expose additional controls only where rendering is verified for the installed sign. Store style settings with cue content and include them in display output and portable templates.
- Determine whether styled content is rendered by the controller or by the application into a supported pixel payload. Do not assume native rich-text or color support. If a requested style cannot be rendered readably or transported, document the gap and resolve it before claiming the requirement is met; never silently discard formatting.
- **Preview Workflow:** Preview new or edited custom text on an enlarged 32x16 grid, including animation when applicable, before the operator presses Send. Saved quick cues with current physical-layout approval remain one-tap actions. Untested or changed saved cues follow the preview-and-confirm rule below. During setup, provide an explicit Test on Sign action and check sample countdowns/cues from the speaker's position before approving layouts for live use. A physical test necessarily sends content to the sign and must be clearly identified as such. Disable Test on Sign throughout a started service, including paused and expired segments, and enforce this restriction in the output layer as well as the UI. On-screen previews remain available. Outside a started service, serialize test output and suspend automatic replay of previous output during the test; leaving test mode restores the prior app-owned output if available. If prior output is unknown, explain that the test remains on the sign until replaced. Starting a service exits test mode before sending its countdown.
- **Layout Approval Rules:** Store physical readability approval locally against a fingerprint of the exact text, font/font version, size, bold/italic styling, alignment, positioning, color, effects, scrolling/flashing speed, renderer version, and target controller/firmware/panel profile. Countdown approval covers the time format and tested digit range rather than each changing second. Record the approval timestamp after an operator performs Test on Sign and confirms readability from the speaker's position. A changed fingerprint invalidates approval for the changed layout; unchanged active-service snapshots retain matching approval. A different sign/profile or rendering implementation requires a new test.
- **Untested Layouts:** Mark changed, new, and imported layouts **Not tested on sign** unless an identical locally approved fingerprint already exists. Physical approval is local evidence and is not exported or trusted from imported JSON. On-screen preview alone never grants physical approval. For an untested saved cue, tapping it opens a preview and explicit Send Untested Cue confirmation; after dismissal, sending it again requires the same confirmation until physically approved. New live custom text uses its required preview with a visible Not tested on sign label and explicit Send Untested Text action. This permits urgent messages without enabling physical setup tests during a service.
- **Automatic Screen Approval:** Before Start First Segment, list any untested countdown, zero-time, or end-screen layouts. The operator must either cancel and test them during setup or explicitly accept using those untested layouts for this service only. Recheck the current target profile and layout fingerprints at start. A target-profile change during a service must obtain the same explicit acceptance before output resumes if it invalidates approval. This acceptance does not mark layouts physically approved. Timing state remains governed by the existing start/reconnect rules.
- **Near-Instant Cue Response:** Minimize delay from the actual user Send/quick-cue tap to the first visible frame of that cue on the physical sign. Start measurement at the physical tap, not after application acceptance; include input handling, validation, persistence, rendering, queueing, transmission, and controller processing. Use synchronized instrumentation or a recording that shows both the tap and sign to establish the measurement interval. Set an initial engineering acceptance target of **250 ms or less for at least 95% of cue sends, with no send exceeding 500 ms**, on an already connected, healthy local Wi-Fi link. These are targets to verify, not measured capabilities. Measure at least 100 sends on the target Android device/controller under representative booth conditions, including replacement of an active cue and sending during timer updates. Record median, 95th-percentile, maximum, and failed deliveries; a failed send fails the test rather than being omitted. Measure visible output, not merely socket-write completion; also record the elapsed time from the same tap until the entire scrolling message has passed through the display once. Test the longest supported cue at its configured speed and include full-message readability in setup approval. If the hardware cannot meet these targets, report measured results and obtain a product decision before changing acceptance thresholds. Show intended output and delivery status separately; reconnect delays are tested separately.

#### 3.5 Saved State and Recovery
- Persist the active service snapshot, segment, timer state and timing references, adjustments, active alert with formatting, zero/end display settings, service lifecycle state, and undo checkpoint. Persist logical changes atomically before treating them as committed. Persist sufficient timing anchors to reconstruct elapsed time without a disk write every second.
- On reopening after closure, crash, or interruption, automatically restore the saved service and continue its timer accounting for elapsed time while closed. A paused timer remains paused; an expired timer shows the configured zero-time screen. Restore any active alert locally and reconnect to send the latest intended output only when the recovery-age rule below permits transmission. An ended service restores its end-screen state, not a running timer; automatic retransmission is subject to the same recovery-age rule. A Ready service restores Ready without starting timing or sending its first segment; an idle session sends no automatic content.
- **Recovery Age and Resend Confirmation:** Automatically resume output after an interruption shorter than 30 minutes when timing is trustworthy. After 30 minutes or more, or when elapsed absence cannot be established reliably, restore and calculate the service locally but hold all automatic display writes. Show the service name, last activity time, active cue if any, and current intended output. Offer **Resume Output**, **Dismiss Alert and Resume Timer** when applicable, or **Keep Output Disconnected**. For an ended service label the resume action **Send End Screen**. Explicit selection must be saved before sending the current value; never send a cached time from when the dialog opened. Countdown accounting continues locally while waiting. Manual disconnection remains in force until explicitly reconnected. Idle and Ready states still send no service output.
- Track output-session activity using a persisted checkpoint at least every 60 seconds while its execution loop is active, and on lifecycle transitions where available; this is separate from per-second rendering and does not require per-second disk writes. Use the last trustworthy checkpoint conservatively to estimate absence. UI inactivity alone is not an interruption when the execution loop remains active. Apply the age rule to long connectivity outages as well as process reopening, and persist an output-held decision so reopening cannot bypass it. A fresh service started explicitly establishes a new output session.
- **Persistence Failure:** Commit state changes atomically before scheduling their output or reporting success. If persistence fails, retain the last committed logical state, show the failed action and a Retry option, and send no output for that failed action. An already-running committed timer continues accounting for elapsed time; rollback must not freeze or reset it. Apply this behavior to service actions, cues, settings, approval records, and imports. Retry revalidates the action against the current service revision and recalculates time; reject stale retries. A failed background activity checkpoint marks recovery evidence uncertain and shows a warning while the committed timer continues. If no valid saved state can be recovered, report recovery failure and hold output instead of inventing or resetting a service silently.

- Use a suspend-aware monotonic source where available. Detect device reboot or invalidated monotonic references and use persisted wall-clock recovery anchors as a fallback, documenting that offline clock changes can make this fallback uncertain. Surface detected timing uncertainty rather than claiming exact recovery.
- Distinguish timer reconstruction from physical updates: when Android prevents execution or the app is terminated, continued sign updates cannot be presumed. Verify actual sign behavior and the supported background-running mechanism. Reopening must restore the current state rather than replay missed updates.

#### 3.6 Output Ownership and Stale-Request Protection
- Give each output session a unique identifier and each committed display-state change a monotonically increasing revision. Tag queued work, retries, and completion callbacks with both identifiers. Verify ownership before dispatch and before using completion results; discard superseded work. Network retry never repeats the underlying service action.
- Successfully loading a new timeline into Ready cancels pending output and retries from the previous session, including an undelivered Hallelujah screen. Opening or cancelling the selection popup before loading does not cancel them. Cancelling Ready does not resurrect old retries. Start First Segment establishes current ownership before sending; ending a service supersedes its countdown/alert work with the end-screen revision. Explicit disconnect, recovery output holds, and test-mode transitions also invalidate pending display work as appropriate.
- Serialize transport operations and follow verified controller ordering/cancellation behavior. Already-transmitted packets cannot be assumed retractable: drain or safely reset the transport as supported before publishing newer output, then send the latest state. A late acknowledgement must never change the current service state or trigger another obsolete send. Demonstrate the stale-output handling on hardware; document and resolve any transport limitation that prevents reliable ordering.

#### Shared Input Limits and Validation
Apply the same validation rules to manual creation/editing, CSV/JSON imports, and live input where applicable. These are version-1 application limits; validate rendering within them during hardware testing rather than silently truncating input.
- Template and segment names: 1–80 Unicode code points after trimming; reject blank names. Apply the same case-insensitive template-name uniqueness rule during creation, renaming, and import.
- Timeline: 1–200 segments; each configured duration is an integer from 1 to 99 minutes.
- Live remaining time: 0–99:59, displayed as MM:SS. Add accepts nonnegative integer minutes and seconds from 0–59 with a positive total. Reject Add or +2 minutes if the resulting remaining time would exceed 99:59; explain the limit and leave state unchanged. Subtraction clamps at zero. These live adjustments do not rewrite the saved template duration.
- Custom cue, zero-time, and end-screen text: 1–160 Unicode code points, with non-whitespace content. Reject unsupported characters/styles with an explanation; never silently omit or substitute them. Text too wide for a static layout must use a verified scrolling or alternate text layout approved in preview, or be shortened before sending/saving. No image content is accepted for the zero-time screen.
- Import file: at most 1 MiB (1,048,576 bytes), containing one template and no more than 200 segments. Reject oversized files before parsing. Validate all imported fields and limits before enabling Accept Import; any violation blocks the complete import.

## 4. Hardware Connectivity & Protocol Investigation
The intended approach is to tear down and examine the LedArt-Lite Android APK, understand its hardware communication and operational behavior, and implement the relevant operations in this application. Do not invent packet formats, ports, commands, or hardware capabilities. Do not write replacement controller firmware.

1. **Identify the Investigation Inputs:** Record the exact installed Huidu controller model, firmware version, panel configuration, and LedArt-Lite APK version and file hash. The target application version is **LedArt-Lite 2.3.14**, as specified by the product owner. The product owner will supply the LedArt-Lite 2.3.14 APK and has confirmed access to the physical sign for validation. The APK has not yet been supplied; record its hash and verify its version when received. Identify the controller model, firmware, and panel configuration from the sign during investigation. Use the supplied APK and physical sign as the primary implementation references; access does not by itself mean hardware tests have been completed.
2. **APK Examination:** Inspect the APK's manifest, resources, decompiled application code, and relevant bundled/native libraries to locate connection setup, discovery, transport, command framing, display/program updates, acknowledgements, and error handling. Trace the operations needed for countdown output, text cues, clearing/replacing a cue, styled text rendering (including bold and italic), and reconnection. Record unresolved behavior explicitly.
3. **Observe and Compare Real Operations:** Where available, observe LedArt-Lite communicating with the test controller and compare captured exchanges with the APK findings. Verify device addressing, listening ports, connection/handshake sequence, framing, encoding, checksums, acknowledgements, and any required initialization. The addresses `192.168.4.1` and `10.10.10.1` are candidate examples, not confirmed defaults for the installed device.
4. **Local Access Point Routing:** The operator connects the application device to the controller's Wi-Fi network. The application connects using the verified device address and transport. Automatic Wi-Fi switching is platform-dependent and must not be assumed available.
5. **Protocol Abstraction Layer:** Implement a communication adapter that translates the application's desired display state (`seconds_remaining` or active `alert_string`) into the verified controller operations. Keep countdown state and alert priority independent of transport details. Internal `TIMER` and `ALERT` priority flags are application concepts; do not assume the controller protocol implements these flags.
6. **Hardware Feasibility Gate:** Before completing the full application, demonstrate on the actual target controller: a readable countdown with sustained updates; replacement by a text cue; restoration of the current countdown; and recovery after a Wi-Fi disconnect. Measure update and cue latency, establish supported refresh frequency, and determine whether updates require program uploads or whether a native timer/live-update operation is available. If the controller cannot support the requested behavior, document the limitation and resolve the product requirement before claiming support.
7. **Preserve Hardware Configuration:** Identify existing panel settings before testing and preserve them. Establish whether frequent updates use temporary display operations or persistent program writes; validate the intended update mechanism before sustained testing.
8. **Investigation Deliverables:** Produce a concise protocol specification, evidence references to APK code or observed exchanges, representative request/response fixtures, a compatibility record for the tested model/firmware, and a minimal hardware demonstration. Clearly distinguish verified behavior from hypotheses and untested controller variants.

## 5. Verification & Testing Requirements
- **Hardware Mocking:** Build local test endpoints matching the verified transport and observed protocol behavior. Use these to test countdown logic, template transitions, priority overrides, and recovery. Mocks validate application behavior against the implemented model; they do not establish physical controller compatibility. Keep real-hardware verification separate.
- **Countdown Accuracy:** Test delayed callbacks and interrupted network activity. For example, after 90 seconds of elapsed time, a running 10-minute timer must calculate 8:30 regardless of callback count. Test explicit pause/resume, time adjustments, and alerts that leave the countdown running. Changing the device's wall clock must not change an active countdown while its monotonic reference remains valid; test reboot recovery separately.
- **Controlled Reconnection:** On connection failure, keep the dashboard and authoritative timer responsive. Retry using bounded exponential backoff, initially after approximately 1 second, then 2, 4, 8, and up to a maximum of 15 seconds between attempts, with small jitter and finite per-attempt timeouts. Continue while the live display session is active; stop on explicit disconnect or when the output session is closed. Ending a service still requires delivery of the end screen; continue bounded retries for that pending display state until delivered, explicitly disconnected, superseded by another session, or held by the recovery-age rule. Permit only one connection attempt at a time and reset backoff after a verified successful connection. Tune timeout values against the observed protocol.
- **Connection Failure Detection:** Establish a protocol-specific liveness mechanism during APK/sign investigation: finite acknowledgement deadlines, or a verified non-display status request when acknowledgements are unavailable. Record the chosen timeout, probe interval, and missed-response threshold in the protocol specification before release. Treat explicit transport errors or loss of the selected Wi-Fi link as connection failure immediately; transition on missed responses according to the verified policy and begin bounded reconnection. Do not invent heartbeat packets or infer health solely from successful writes. Keep probes from delaying cue output. If no reliable feedback exists, label delivery Unverified and document the detection limitation rather than claiming confirmed connectivity. Validate against an unresponsive controller as well as Wi-Fi disconnection, including while a static alert or end screen is displayed.
- **Visible Connection State:** Show clear states such as Connected, Reconnecting, and Disconnected, including a prominent indication that the physical display may be stale. Do not claim that content is displayed solely because a socket write succeeded. Show transport/connection status separately from Last update confirmed, its timestamp, or Delivery unverified. Use protocol acknowledgements when available and document what they actually confirm; never equate receipt with visible rendering unless verified.
- **Latest-State Recovery:** Retain the latest intended display state instead of accumulating missed updates. After reconnection and required initialization, apply current session ownership, recovery-age, and approval checks first. Held output sends nothing until explicitly released; idle and Ready sessions send no new service output; otherwise send the latest intended output: the end screen for an ended service; otherwise the active alert if present; otherwise the zero-time screen if expired or the current countdown if not. An ended service cannot retain an active alert. Discard stale queued countdowns and superseded or dismissed alerts. Serialize output so older timer work cannot overwrite a newer alert; follow the verified transport's cancellation/completion behavior for work already in flight.
- **Recovery Acceptance Tests:** Disconnect at 8:30 and reconnect 30 seconds later: the application must send 8:00, without replaying missed values. Repeat with an active alert, an alert dismissed while disconnected, and an explicitly paused timer. Verify reconnect attempts follow the bounded schedule and do not freeze the UI. Confirm the physical display behavior on the target hardware as well as in mocks.

- **Service Lifecycle Tests:** Verify selecting/creating a timeline, cancelling Start Service, explicitly starting the first segment, final-segment behavior, and confirmed End Service with default Hallelujah and formatted custom text.
- **Zero-Time Tests:** Verify the 00:00 default and custom screen, no negative time or automatic advance, alerts covering expiry, dismissal after expiry, and adding/subtracting time at zero.
- **Advance and Undo Tests:** Repeated taps and confirmation retries must cause only one transition. Verify cancellation, advancing under an alert, undo of running/paused/expired segments, persistence of the checkpoint, and no undo after End Service.
- **Isolation and Recovery Tests:** Template/settings changes must not alter a live snapshot. Test screen lock, backgrounding, process termination, reopening, and reboot fallback; running time must account for absence, paused time must remain fixed, and an ended service must not restart. Document any uncertainty after clock changes across reboot.
- **Formatting and Readability Tests:** Verify bold, italic, and other exposed styles survive saving, sharing, restoration, and actual display rendering. Check countdown, zero-time, end-screen, and long-cue layouts from the speaker's position, including scrolling and clipping. Verify that new or edited custom text is previewed before sending, physical-sign readability is checked during setup, and saved quick cues remain one-tap actions.

- **Control Tests:** Confirm Pause/Resume, Add, -2 minutes, and +2 minutes are separate controls; validate custom-duration entry, cancellation, duplicate-confirm protection, exact 120-second adjustments, zero clamping, paused adjustments, and preservation of active alerts.
- **Import Tests:** Cover CSV and versioned JSON, malformed files, invalid rows/settings, empty files, unsupported schema versions, name conflicts, cancellation, preview accuracy, and repeated acceptance taps. One invalid row must prevent every row from being imported. Name conflicts must block acceptance until explicitly resolved. Verify no incoming data is saved before Accept Import and no import changes the active service or sign.
- **Cue Latency Tests:** Measure the tap-to-visible-frame target defined in Section 3.4 on actual hardware while connected. Record the test environment and complete results; socket mocks cannot establish physical cue latency.

- **Ready-State Tests:** Loading, cancellation, reopening, and reconnection must not start timing or send the first segment before Start First Segment. Verify disabled controls and single-commit start behavior.
- **Setup Isolation Tests:** UI and output-layer checks must reject Test on Sign during running, paused, and expired services. Verify on-screen previews still work, test mode exits before service start, and connection corrections preserve current timing and alerts without modifying panel configuration.
- **Undo Confirmation Tests:** Test the 10-second boundary, adjusted and paused/resumed new segments, reopening, uncertain elapsed time, cancellation, and checkpoint consumption. Verify advancing from pause starts the next segment running and undo restores the prior pause state.
- **Validation Boundary Tests:** Exercise all shared limits at and above their boundaries across manual entry and both import formats. Verify JSON excludes local hardware settings; import rejects them; zero-time screens accept formatted text only; excess duration and unsupported text are never silently truncated.
- **Connection Detection Tests:** Exercise missing responses, transport failures, Wi-Fi loss, and static-output states. Verify transition timing against the documented protocol policy and distinguish connection status from update confirmation. Physical delivery claims must match observed acknowledgement semantics.

- **Session Ordering Tests:** End a service while disconnected, load another into Ready, and reconnect: the old end screen must not be resent. Start the new service and inject delayed callbacks/retries from the previous session; none may overwrite its output or alter its state. Verify cancellation of Ready does not resurrect old writes and test actual transport ordering.
- **Recovery-Age Tests:** Test interruptions immediately below and at 30 minutes, overnight restoration with an active alert, extended Wi-Fi outages, uncertain clocks, explicit disconnect, and repeated reopenings while held. Verify no content is sent before confirmation when required; resumed timers use the current value and ended services stay ended.
- **Settings and Persistence Tests:** Verify defaults seed new templates only, CSV acceptance matches previewed defaults, JSON retains its settings, and template edits do not change a snapshot. Inject storage failures during advance, cue send, end, import, approval, and background checkpointing; verify atomicity, truthful failure feedback, continued committed timing, and safe retry without duplicates.
- **Layout Approval Tests:** Verify text/style/effect/font/renderer/profile changes invalidate matching approval, imports cannot confer approval, countdown ticks do not invalidate an approved digit range, and unchanged snapshots retain their matching record. Test preview-and-confirm sending of untested cues, service-only acceptance of automatic screens, and the physical-test lockout during live operation.

### Full-Service Endurance Acceptance Test
- Run on the intended Android device and physical sign for the longer of **3 hours or the planned service duration**, using a representative multi-segment timeline. Repeat for each device/controller configuration claimed as supported. Use a separate fault-recovery run for deliberate process termination so the continuous-service run remains measurable.
- Include at least 100 cue sends distributed across the run; formatted/scrolled cues, replacement and dismissal; pause/resume; Add and +/-2-minute adjustments; confirmed advance and undo; zero-time and end screens; and at least 15 minutes with the screen locked/background operation. Introduce at least three brief Wi-Fi interruptions at different points, including during an alert. Exercise an interrupted end-screen delivery followed by a new service. Test long-outage recovery holds separately without shortening the required continuous run.
- Compare authoritative remaining time against an independent elapsed-time reference, accounting for intentional pauses and adjustments. Require no accumulating drift and no more than 1 second of discrepancy at sampled checkpoints. While connected and execution is supported, require the physical countdown to stay within one displayed second of the authoritative value. Measure stale output separately during intentional outages and require correct latest-state restoration after verified reconnection.
- Require no unplanned crashes, unresponsive UI, duplicate transitions, lost committed state, or superseded output replacing current output. All connected cue sends must meet Section 3.4 latency criteria. Recovery must satisfy the documented detection/backoff policy; planned faults are not excuses for stale replay. Record any failure and rerun the affected acceptance scenario after correction.
- Record Android/app/controller/firmware versions, panel profile, timeline, power/network conditions, latency statistics, timing checkpoints, memory usage and battery/thermal observations at start and regular intervals, fault/recovery logs, and operator readability results. Investigate sustained resource growth or thermal-related degradation before release. The report must distinguish continuous execution, deliberate disconnections, and process-termination recovery; it must not imply that display updates continued while execution was unavailable.
